# TrustTunnel на ASUSWRT-Merlin: исследование и решение для тестовой сборки

Дата последней проверки источников: **30 сентября 2026 года**. Цель — клиентский аддон для **RT-AX86U с Entware**, встроенный в раздел VPN. Базовая установка проверена на Merlin 388.12_2; совместимость новых функций и полная сетевая приёмка остаются незавершёнными. Этот документ описывает принятые решения; результаты запусков находятся в [TEST-REPORT.md](TEST-REPORT.md), аппаратная приёмка — в [HARDWARE-TESTS.md](HARDWARE-TESTS.md).

## Что дали предложенные примеры
Дополнение после аппаратной установки: в [httpd/web.c тега 3004.388.12_2](https://github.com/RMerl/asuswrt-merlin.ng/blob/3004.388.12_2/release/src/router/httpd/web.c#L5487) `update_variables` содержит `notify_cmd[128]` и копирует туда action_script. Поэтому для browser transport применяется максимум 127 символов, хотя rc/services.c использует буфер 256. Это объяснило фактический отказ первой длинной части на AX86U; протокол изменён на шесть коротких частей одного RSA-блока.

Репозитории — первичные источники о собственных реализациях, статья — объяснение и демонстрация XrayUI. Источником контракта Merlin служит документация прошивки; контракта TrustTunnel — код и спецификации закреплённого релиза. При расхождении README с исходниками приоритет получает код этой версии.

Из примеров принят последовательный сценарий: **подготовить подключение → проверить параметры → выбрать сети → применить → проверить состояние и реальный трафик**. Для первой проверяемой версии достаточно одного сервера TrustTunnel, нескольких исходных сетей и понятного поведения при остановке клиента. Редактор всех возможностей Xray или AmneziaWG здесь не нужен.

## Нативный интерфейс и приватность подключения

[Merlin Addons API](https://github.com/RMerl/asuswrt-merlin.ng/wiki/Addons-API) предусматривает пользовательские ASP-страницы, выделение свободной страницы через `am_get_webui_page`, интеграцию меню и передачу общих настроек через `amng_custom`. Документированные пределы общего хранилища: **2999 символов на значение и 8 КиБ суммарно**. Это общее пространство аддонов, а не специально выделенное хранилище секретов.

Решение в текущем коде:

- Страница [trusttunnel_page.asp](../addon/trusttunnel_page.asp) использует оболочку и штатный веб-сервер Merlin; отдельный HTTP-сервис не устанавливается.
- Ручная форма и разбор `tt://` работают локально в браузере. Основной путь сохранения шифрует endpoint временным RSA-OAEP ключом и передаёт ciphertext через штатные события Merlin; контроллер повторно проверяет документ и применяет его транзакционно. Реальная совместимость с httpd/auth/CSRF целевой прошивки ещё не подтверждена.
- Запасной путь скачивает `trusttunnel-endpoint.json`: файл переносится по SCP/SFTP и импортируется командой `trusttunnel.sh import-endpoint`. Импорт выполняет повторную проверку, сохраняет предыдущую приватную конфигурацию и записывает новый файл с ограниченными правами. Обычный импорт работающего профиля запрещён.
- Новый UI не записывает `amng_custom`. Endpoint и политика передаются приватным каналом либо экспортируются как JSON для импорта по SSH.
- Пароль не помещается в NVRAM, общие настройки аддонов, открытый каталог страницы или публичный статус. Форма не использует localStorage для подключения. Экспортированный файл содержит пароль, поэтому временные копии нужно удалить после переноса.

**Браузерное приватное применение реализовано экспериментально и проверено только локальной имитацией.** На целевой прошивке ещё нужно подтвердить штатные авторизацию/CSRF, пределы и порядок service-event, доступ к OpenSSL и отсутствие открытого секрета в журналах httpd/событий. Экспорт/SSH остаётся проверяемым запасным путём.

В релизе есть Linux-архивы aarch64, armv7, mips, mipsel и x86_64. Для AX86U выбран aarch64; наличие архива не доказывает совместимость с конкретным ядром Merlin. [Релиз v1.1.5](https://github.com/TrustTunnel/TrustTunnelClient/releases/tag/v1.1.5).

Поля стабильной версии проверены по [парсеру конфигурации v1.1.5](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/trusttunnel/src/config.cpp) и [общей модели endpoint](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/trusttunnel/settings/src/lib.rs). Ограничения справа — решения этого аддона, а не недостаток upstream.

**SNI и TLS fingerprint — разные параметры.** `custom_sni` выбирает имя для TLS ClientHello. Настраиваемый `tls_profile` выбирает представление ClientHello, имитирующее определённый клиент. На дату исследования `tls_profile` присутствует в master/Unreleased, но не входит в стабильную схему v1.1.5; поле не добавлено в форму. Это также не отпечаток сертификата и не проверка его подлинности. Основание: [CHANGELOG с секцией Unreleased](https://github.com/TrustTunnel/TrustTunnelClient/blob/master/CHANGELOG.md).

## Импорт ссылки без потери существенных настроек

Официальный формат — `tt://?` с Base64url-кодированными двоичными TLV-полями. Это не JSON и не набор обычных URL-параметров. Версия формата находится внутри данных; отсутствие версии означает v0. Адреса могут повторяться, а цепочка сертификатов передаётся как DER. Основание: [спецификация Deep Link](https://github.com/TrustTunnel/TrustTunnel/blob/v1.0.33/DEEP_LINK.md).

Клиент v1.1.5 закрепляет библиотеку импорта из TrustTunnel v1.0.33; с ней сверена реализация [connection.js](../addon/web/connection.js). [Зафиксированная зависимость](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/trusttunnel/Cargo.lock), [upstream decoder](https://github.com/TrustTunnel/TrustTunnel/blob/v1.0.33/deeplink/src/decode.rs), [DER→PEM](https://github.com/TrustTunnel/TrustTunnel/blob/v1.0.33/deeplink/src/cert.rs).

Правила нашего импорта:

- Проверяются Base64url, UTF-8, длины TLV, QUIC VarInt и переполнение. URI ограничен 32 КиБ, PEM — 16 КиБ. Будущая версия формата отклоняется.
- Старый `tt://` без вопросительного знака принимается с предупреждением.
- Повтор одиночного поля обрабатывается по правилу **последнее значение побеждает**, с предупреждением пользователю. Повтор адреса добавляет адрес. Неизвестный тег пропускается с предупреждением, как требует расширяемый формат; его номер не преобразуется в известный тег по младшему байту.
- Неподдерживаемые известные параметры не отбрасываются: импорт завершается понятной ошибкой. Исходную конфигурацию следует сохранить и использовать совместимый клиент либо расширить проверенную схему аддона.
- `has_ipv6=true` — сообщение о способности сервера, а не требование обязательно использовать IPv6. Импорт разрешён с предупреждением об IPv4-профиле и блокировке IPv6 на выбранных мостах.
- При отсутствии DNS сохраняется пустой список с предупреждением. Автоматической подстановки резолвера нет; для запуска нужен DNS в конфигурации подключения.
- Разбор сертификата проверяет обрамление DER/PEM. Он не подтверждает доверие, срок действия или принадлежность сертификата серверу: это проверяет TLS клиента при подключении.

Официальная утилита тоже умеет импорт: `setup_wizard --mode non-interactive --deeplink URI --settings FILE`. Для веб-пути она не используется, поскольку секретный URI оказался бы в аргументах процесса. У Linux CLI v1.1.5 нет отдельной команды `--check` или `--validate`; успешный разбор JSON нашего аддона нельзя называть полной проверкой клиентом. [CLI wizard](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/trusttunnel/setup_wizard/src/main.rs), [CLI клиента](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/trusttunnel/src/trusttunnel_client.cpp).

## Основная сеть и три гостевые: как выбирать корректно

**SSID, Linux bridge и IPv4-подсеть не являются взаимозаменяемыми понятиями.** Несколько беспроводных имён могут относиться к одному мосту; изоляция гостей сама по себе не доказывает отдельную маршрутизируемую подсеть. Фактический результат зависит от модели, версии прошивки и настроек сети. Код Merlin управляет LAN через имена интерфейсов и состав моста, а не через условные номера строк формы. [Первичный код LAN Merlin](https://github.com/RMerl/asuswrt-merlin.ng/blob/main/release/src/router/rc/lan.c).

У ASUS отдельная возможность Guest Network Pro создаёт сети/VLAN, но её документация перечисляет определённые модели, включая **RT-AX86U Pro**. Это не подтверждает такую же поддержку у **RT-AX86U** и не задаёт имена `br1`, `br2`, `br3`. [Официальная документация Guest Network Pro](https://www.asus.com/support/faq/1053601/).

Поэтому интерфейс показывает фактически обнаруженные SSID и объединяет их по реальным L3-сетям. Bridge недоступен для редактирования; при отсутствии данных фиктивные br0–br3 не создаются. Аддон не создаёт гостевые SSID, VLAN или подсети и не меняет их существующую изоляцию.

Политика schema 3 содержит `networks[]`; у каждой выбранной сети есть `lan_if` и список `sources` в CIDR. Можно отметить все или несколько строк. Поддерживается до 16 различных мостов и 32 исходных CIDR суммарно; один мост с несколькими подсетями описывается одной строкой. Schema 1 остаётся форматом одной сети. Контракт проверяется в [validate.jq](../addon/share/validate.jq), форма — в [trusttunnel.js](../addon/web/trusttunnel.js).

Маршрут выбирается по **входному bridge и исходному IPv4 CIDR одновременно**. Если основная и гостевая Wi-Fi-сети приходят через один мост с одной подсетью, такая политика не умеет независимо выбирать их по имени SSID. Можно выбрать конкретные устройства через /32; для независимых сетей потребуется предварительно подтверждённое разделение сети. Автоматически перестраивать LAN в рамках первого теста аддона нельзя.

Перед включением составляется таблица «SSID → беспроводной интерфейс → bridge → адрес/маска». Для неё нужны реальное состояние интерфейсов, `brctl show` либо аналогичный просмотр bridge, IPv4-адреса и настройки DHCP. Один образец `br0–br3` или перечень SSID не заменяют такую проверку.

## Кто управляет маршрутами и что происходит при остановке

Текущий [render.jq](../addon/share/render.jq) задаёт `device_name="tt0"`, `use_existing=false`, `included_routes=[]`, `excluded_routes=[]`, `change_system_dns=false`. Клиент создаёт TUN, а маршрутизацией выбранных LAN управляет аддон. Для upstream пустой `included_routes` отключает настройку и очистку собственных маршрутов/правил, включая таблицу 880. В режиме `use_existing=true` клиент сохранял бы адреса оператора, но всё равно поднимал бы интерфейс и выставлял MTU. [Linux TUN v1.1.5](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/net/src/os_tunnel_linux.cpp).

Собственная таблица 871 и приоритеты 17100–17131 позволяют ограничить изменения. При обнаружении неизвестного владельца таблицы, цепочек или интерфейса включение должно прекращаться. Правила защиты ставятся до доступности маршрута через TUN; запрещающий маршрут остаётся запасным. Пауза и падение процесса сохраняют защиту; явное отключение снимает только принадлежащие аддону правила. Изменение активного набора сетей запрещено до реализации безопасного перехода между политиками. Текущий план правил: [network.jq](../addon/share/network.jq).

IPv4-защита применяется к выбранным сочетаниям bridge/CIDR. IPv6-защита шире: **на каждом выбранном bridge блокируется весь IPv6-транзит и IPv6 DNS к роутеру**, включая устройства вне выбранных IPv4 CIDR. Это требует отдельного подтверждения в форме. Такая защита не означает отключение самого IPv6 в LAN, прекращение RA или блокировку всех локальных IPv6-служб роутера.

Перехват обычного DNS относится к TCP/UDP 53. Проверять нужно также приложения с DoH/DoT и сохранённые соединения. При полном туннелировании они не должны получать обходной WAN-путь, однако утверждать это без наблюдения трафика на устройстве нельзя. Поведение аппаратного ускорения, conntrack и гостевой изоляции относится к аппаратным тестам.

## Как получить проверяемый результат

| Этап | Что он доказывает | Что ещё не доказано |
| --- | --- | --- |
| Локальные тесты парсера и схем | Корректность преобразования, сохранение полей, ошибки на повреждённых/неподдерживаемых данных. | Доверие TLS и доступность сервера. |
| Тесты shell с подменёнными сетевыми командами | Порядок операций, обработку ошибок, защиту чужих ресурсов, откат и совместимость схем. | Реальное поведение ядра, iptables и ускорения ASUS. |
| Открытие preview и проверка интерфейса | Работу формы, импорта, сообщений, выбор сетей и экспорта. | Работу штатного `start_apply.htm`, авторизации и hook на роутере. |
| Проверка устройства без включения VPN | Модель, прошивку, архитектуру, зависимости, топологию и отсутствие конфликтов. | Прохождение клиентского трафика. |
| Поэтапный сетевой тест | Реальные маршруты, DNS, поведение паузы/сбоя, сохранение управления и изоляции сетей. | Работу всех других моделей и прошивок. |

Первый сетевой тест следует выполнять с проводным доступом к управлению и одной контролируемой сетью или устройством /32. Затем проверяются остальные гостевые сети по одной и совместно. Для каждой выбранной сети нужны проверки внешнего IP и DNS, а для невыбранных — сохранение ожидаемого выхода. Отдельно проверяются остановка клиента, недоступный сервер, перезапуск firewall/WAN и перезагрузка роутера. Неожиданный выход выбранного трафика через WAN — неуспешный тест, даже если интерфейс показывает работающий процесс.

Бинарник берётся из закреплённого официального релиза. Релизный процесс включает отдельные GPG-подписи клиента и wizard; проверка подписи и хеша предшествует установке. [Процесс выпуска](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/.github/workflows/build-console.yml). Проверка ELF и aarch64 — только предварительный фильтр совместимости.

Признак процесса, наличие `tt0` и рост счётчиков не равны подтверждённому VPN-соединению. Поэтому интерфейс честно различает «процесс запущен», «TUN создан» и необходимость проверки связи. До выполнения аппаратной матрицы результат проекта — **сборка для испытаний**, а не подтверждённая установка на AX86U.

Пользовательский сертификат дополнительно проверяется на роутере до импорта и генерации TOML: каждый PEM-блок должен успешно разбираться `openssl x509`. Некорректный первый или последующий блок, посторонний текст и незакрытые блоки отклоняются. Без OpenSSL непустой custom certificate не принимается; пустое поле использует обычное хранилище доверия клиента. Эта проверка предотвращает молчаливый fallback upstream при ошибке разбора, но не заменяет проверку TLS при соединении.

## Уточнение DNS и SSID в 0.2.1

Реальная привязка на AX86U проверена по [init.c Merlin](https://github.com/RMerl/asuswrt-merlin.ng/blob/main/release/src/router/rc/init.c) и [NVRAM defaults](https://github.com/RMerl/asuswrt-merlin.ng/blob/main/release/src/router/shared/defaults.c): базовые и виртуальные wl-интерфейсы сопоставляются с участниками bridge через ifname/vifnames, а имя читается из соответствующего ssid. Только номер br не является доказательством соответствия.

DNS-путь сверялся с [dns_handler.h v1.1.5](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/core/src/dns_handler.h), [dns_handler.cpp](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/core/src/dns_handler.cpp) и [client.cpp](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/trusttunnel/src/client.cpp). При непустом endpoint.dns_upstreams DNS обрабатывает DNS proxy; при пустом списке включённый в VPN запрос может сохранить исходное назначение. Поэтому адрес назначения DNAT нельзя объявлять альтернативным резолвером, а для используемого внутреннего транзитного пути требуется явно заданный DNS подключения. Соответствие настоящему трафику всё ещё требует проверки на роутере.

## Исключения TrustTunnelClient v1.1.5

[Справочник конфигурации закреплённой версии](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.5/trusttunnel/README.md#exclusions-syntax) определяет верхнеуровневые `vpn_mode` и `exclusions`. В режиме `general` исключения обходят VPN; поддержаны обычный домен, `*.domain`, IPv4 с необязательным портом, IPv6, CIDR и `*:port`. Полный URL и HTTP-путь в синтаксис не входят.

Аддон фиксирует `general`, потому что выбор исходных LAN/устройств уже выполняет его policy routing. IPv4-совместимое подмножество синтаксиса хранится в endpoint JSON и дословно генерируется как TOML-массив после строгой проверки. IPv6-правила не предлагаются: клиент запускается с `has_ipv6=false`, а выбранные bridge получают IPv6 block. `[listener.tun].excluded_routes` остаётся пустым согласно тому же справочнику: `included_routes=[]` отключает управление таблицей 880, которое конфликтовало бы с собственной таблицей 871 аддона. Реальный прямой выход доменных/IP-исключений и DNS-поведение ещё должны быть подтверждены пакетной проверкой на AX86U.

## Уточнение HND на AX86U, 20.09.2026

Изначальное требование `ctf_disable=1` удалено: оно смешивало CTF и HND и требовало глобального ограничения без проверки возможностей прошивки. Штатный VPN Director использует собственные source-policy правила; наличие VPN-клиента не обосновывает отключение ускорения всего роутера. Проверены исходники Merlin 3004.388.12_2 (ссылки в UPSTREAM.md) и доступные механизмы реального роутера.

SKIPLOG вызывает `blog_skip` для совпавших пакетов и продолжает обычную фильтрацию. Alpha.5 применяет его к выбранным IPv4 источникам/ответам и к IPv6 выбранных bridge. После установки guards выполняется `fc flush --if` для выбранного bridge и его участников: уже ускоренные соединения должны снова пройти правила. Глобальные `fc disable`, `runner disable`, NVRAM и общий conntrack не используются. Выключенный аддон не устанавливает эти правила. При выборе отдельных /32 очистка кеша всё равно касается bridge; остальные потоки могут обучаться заново. Это нужно учитывать при последующих измерениях.

Реальный первый запуск подтвердил наличие правил, обмен br1↔tt0 и сохранение Enabled у HW Acceleration/Flow Learning; он не заменяет тесты существующих потоков, IPv6/DNS-утечек, перезагрузки и скорости. Производительность самой VPN-сети ограничивается обработкой TrustTunnel/шифрованием на CPU; скорость остальных сетей пока не измерена, поэтому утверждать отсутствие любого влияния под нагрузкой нельзя.

## Обновления и различие SSID / подсети, 30.09.2026

Ручное обновление CLI выбирает только официальный Linux ARM64 release и проверяет архив/signature/версию до остановки процесса. Метаданные «latest» или hash из API сами по себе не заменяют криптографическую подпись. Публичная nightly не обнаружена; beta и Conan snapshot не подменяют отсутствующий канал. Канал управляет ручным выбором, а не фоновой установкой. Загрузка не блокирует firewall refresh. Подробная реализация/границы восстановления: [CLIENT-UPDATES.md](CLIENT-UPDATES.md), первичные источники: [UPSTREAM.md](UPSTREAM.md).

NVRAM SSID показывает имя Wi-Fi, а не существование отдельной IP-сети. В инвентаризации сохраняются SSID, NVRAM-interface, реальный interface, bridge и адреса самого bridge. Read-only наблюдение подтверждает wl0.2 вместе с main radios в br0 и отдельный wl0.1 в br1. Предположение об отдельной подсети по наличию гостевого SSID или диапазона DHCP br2 было бы ложным. UI показывает Wi-Fi имена отдельно, а общий L3-выбор — явно для всей подсети. Независимая маршрутизация SSID общей подсети требует отдельного проектирования и поддержки interface-level classification; текущая policy строится на iif bridge + IPv4 source и такой возможности не обещает.

Пассивная проверка firewall/rules/счётчиков выбранного трафика безопасна для текущей сети, потому что не останавливает клиент и не меняет правила. Она не может доказать блокировку при обрыве. Для этого нужен контролируемый тест с реальным гостевым устройством и основной управляющей сетью вне политики, включая старые ускоренные соединения, DNS и IPv6.

## Установочная поставка alpha.10

По примеру [install-online.sh](https://github.com/r0otx/asuswrt-merlin-amneziawg/blob/main/install-online.sh) и [build-ipk.sh](https://github.com/r0otx/asuswrt-merlin-amneziawg/blob/main/build-ipk.sh) AmneziaWG подготовлены установка по ссылке и отдельный IPK. Entware принимает tar.gz IPK с debian-binary, control.tar.gz и data.tar.gz; архитектура текущего AX86U проверена настоящим `opkg print-architecture`: aarch64-3.10. Наш пакет хранит установочные источники в /opt/share, а native installer регистрирует интеграцию JFFS. Официальный CLI и пользовательский профиль не входят в payload.

В отличие от динамического latest выбора, наш first-party установщик закрепляет релиз и SHA-256 IPK. CLI при первой установке отдельно проверяется по закреплённым хешам и GPG-подписи. Подготовитель Entware выполняется до opkg install: postinst не вызывает вложенный opkg и не удаляет конфликтующие зависимости под его lock. Семантика install/upgrade/remove и IPKG_INSTROOT сверялась с [OpenWrt packaging](https://openwrt.org/docs/guide-developer/packages) и [opkg-lede](https://github.com/openwrt/opkg-lede/tree/master/libopkg). Offline-root проверяет формат пакета, не доказывает работающую интеграцию VPN.

[Merlin Addons API](https://github.com/RMerl/asuswrt-merlin.ng/wiki/Addons-API) документирован начиная с 384.15. Для этой поставки поддерживаемый минимум выбран **3004.388.12**, поскольку фактические network/TUN/HND проверки выполнены на 3004.388.12_2. Это ограничение поддержки, а не найденная доказательством самая ранняя совместимая прошивка.

## Выбор физических LAN-портов — alpha.15

Начальная карта разъёмов RT-AX86U взята из [таблицы MerVLAN](https://github.com/r80xcore/mervlan): LAN1→eth4, LAN2→eth3, LAN3→eth2, LAN4→eth1, 2.5G→eth5. Это карта модели, а не предустановленный выбор пользователя. Включение проверяет живое членство в br0, WAN, IPTV/агрегацию и идентификатор топологии. Для других моделей карта не угадывается. Поддерживается нетегированный Ethernet; VLAN и AP-режим этой реализацией не подтверждены.

[Цель mark в ebtables](https://netfilter.org/documentation/index.html) записывает skb mark, доступный iptables. Два бита зарезервированы для выбранного порта и временного карантина; остальные биты сохраняются. BROUTING обновляется через атомарный снимок, без очистки общей таблицы. Не используются DROP в BROUTING (там он означает передачу в маршрутизацию), перенос интерфейсов, VLAN, смена DHCP или основного маршрута.

IPv4 получает отдельное правило fwmark/iif br0 в таблицу 871, DNS перенаправляется на прежний внутренний адрес перехвата TrustTunnel. CONNMARK сохраняет только выделенный бит для защиты обратного направления от offload; skb mark обратных пакетов не восстанавливается, чтобы не отправить их снова в TUN. IPv6 отмеченных портов блокируется, включая DNS к роутеру. Выбранные сети по-прежнему блокируют IPv6 на bridge целиком. Изменения работающей политики используют тот же журнал и таймер подтверждения, что и сети: union-классификация карантина, временная новая политика, подтверждение либо возврат.

На роутере 24.10.2026 проверено принятие mark/connmark/SKIPLOG и атомарного ebtables-снимка в неприсоединённых цепочках. Это подтверждает синтаксис и возможности ядра, но не передачу пакетов, физическую нумерацию кабелем или отсутствие утечек. Данные автономной модели не заменяют эти проверки.
