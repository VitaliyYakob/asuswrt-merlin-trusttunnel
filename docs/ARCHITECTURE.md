# Архитектура 0.3.1-alpha.2

## Потоки данных

- Ручные поля/tt:///файл → JavaScript parser → endpoint schema1 (включая необязательный `exclusions`) → приватное сохранение либо JSON export/SSH → TOML → официальный клиент.
- Выбранные сети/устройства/локальные ресурсы → policy schema4 → тот же приватный транспорт → контроллер. Совместимый старый `apply-web-policy` оставлен для отключённого аддона; новый UI его не вызывает.
- Контроллер → ограниченный status.json → XMLHttpRequest страницы. Статус не содержит username, password, ссылку, сертификат или TOML.
- `/www/user/userN.asp` и ресурсы `/www/user/trusttunnel/` обслуживает штатный httpd Merlin. Страница находится в VPN. Отдельного сервера и собственной авторизации нет.

## Политика нескольких сетей

`networks` содержит 1–16 уникальных `lan_if`, каждый с частными каноническими IPv4 CIDR. Общий лимит — 32 записи. Контроллер принимает schema1 с `lan_if/sources` и schema2; при импорте отключённой политики они преобразуются в schema3 с резервной копией и удалением устаревшего DNS-поля.

Пары bridge+source разворачиваются в правила `ip rule ... from CIDR iif BRIDGE lookup 871` с приоритетами 17100–17131. Цепочки DNS/FORWARD ограничены соответствующими ingress bridge и source. Возвратный поток разрешён из tt0 в выбранную сеть. SNAT в POSTROUTING ограничен source и выходом tt0 (в этой цепочке нельзя использовать ingress `-i`). IPv6 REJECT ограничен всеми выбранными bridge целиком. Невыбранные bridge не получают правил TTM.

Собственный `prohibit default` остаётся в таблице 871 при паузе/отсутствии TUN. Основной default route, dnsmasq, resolv.conf, fwmarks и conntrack глобально не меняются. Защита зависит от реального порядка firewall и аппаратного ускорения — обязательны пакетные аппаратные проверки.

## Владельцы

TrustTunnelClient создаёт tt0 и отвечает за транспорт/TLS. Генератор использует `use_existing=false`, `included_routes=[]`, `excluded_routes=[]`, `change_system_dns=false`, `has_ipv6=false`, `skip_verification=false`. Пустые included_routes подавляют управление таблицей 880 upstream-клиентом; маршруты, DNS DNAT, SNAT и guards принадлежат аддону.

Верхнеуровневый `exclusions` имеет другое назначение: при фиксированном `vpn_mode="general"` TrustTunnelClient отправляет совпавшие назначения напрямую. WebUI принимает документированные домены/wildcard, IPv4/CIDR, IPv4:порт и `*:порт`. Он не переносит их в `[listener.tun].excluded_routes`, поэтому клиент не получает владение системными маршрутами. IPv6-формы upstream намеренно не принимаются при `has_ipv6=false` и bridge-wide IPv6 block.

Конфигурация: `/jffs/addons/trusttunnel/config/` (0700), JSON и `.previous` (0600). Runtime: `/tmp/trusttunnel/` (0700). При включённом аддоне обычный импорт запрещён; изменения идут только через транзакцию. В контроллере flock; дочерний клиент закрывает lock FD. PID сверяется по starttime и executable realpath.

## Границы интерфейса

Импорт tt:// не запускает setup_wizard, не использует shell и не отправляет ссылку по сети. Он проверяет формат, а не доступность сервера. Проверку сертификатной цепочки выполняет клиент. Поля name и предупреждения отображаются как текст. Browser downloads создают приватную по содержанию, но не гарантированно 0600 по правам копию — пользователь ограничивает права перед переносом.

Новый канал не читает и не записывает общие settings. HTTPS/Web Crypto получает временный открытый RSA2048 ключ; каждый блок RSA-OAEP SHA-256 содержит ID сессии, индекс, число блоков и до 128 байт JSON. Шифртекст разбивается на шесть событий, каждое не длиннее 127 символов (буфер notify_cmd[128] в httpd Merlin). Контроллер принимает части последовательно, допускает повтор последней подтверждённой части, проверяет зашифрованный заголовок и применяет документ только после полного приёма. Закрытый ключ, буферы и расшифрованный JSON удаляются после завершения/отмены/истечения срока. Ограничения: 64 КиБ, 512 блоков, одна передача, 2 часа. Криптопримитивы не заменяют HTTPS и аутентификацию Merlin.

JSON-конверт содержит `version`, `revision`, `kind`, `data`. Ревизия меняется при записи/откате; совпадение проверяется под lock. ID операций хранятся только в runtime: до 256 записей, завершённые старше суток удаляются, публичный статус содержит 16 последних. После перезагрузки история ID не сохраняется. Повтор commit с существующим ID не исполняет действие снова. Подтверждение отправки формы не считается успехом.

## Активная транзакция

Перед изменением проверяются обе конфигурации и отсутствие чужих TXN-цепочек. В приватном `config/transaction/` сохраняются old/new endpoint/policy и manifest. Отдельные `TTM4_TXN/TTM4_TXNI/TTM6_TXN/TTM6_TXNI` блокируют объединение старых и новых источников. Под этой блокировкой заменяются собственные рабочие правила и конфигурация. В фазе trial новые источники возвращаются в обычные guards, удалённые старые остаются заблокированы до подтверждения.

При подтверждении удаляется карантин. При ошибке или истечении 180 секунд восстанавливаются оба старых JSON и прежний paused intent; сбой восстановления оставляет журнал и блокировки. Cron/boot повторяет восстановление. После потери runtime-маркеров ресурсы проверяются на чужую занятость. `recover` не захватывает неизвестные таблицы/цепочки. Несколько таблиц firewall не образуют единую kernel-транзакцию; пакетные свойства требуют отдельной проверки.

Schema4 добавляет обязательный hash состава bridge/его CIDR и `local_access`. Предварительная проверка сопоставляет их с текущей инвентаризацией. Исключения добавляют connected routes только в таблицу 871; filter RETURN сохраняет последующие ограничения Merlin. SSID не входят в hash. DHCP reservation не создаётся аддоном; /32 остаётся привязкой к адресу.

Статус всегда содержит `connection_verified:false`. Backoff ограничивает неудачные попытки запуска, но не восстановление guards. Счётчики TUN, процесс, jump и prohibit route — диагностические признаки, не проверка доступности через VPN.

Инвентаризация читает sysfs bridge/brif и IPv4-адреса, а также только NVRAM wlN_ifname, wlN_vifnames, wlN.M_ifname и ssid фактических участников bridge. Номер bridge не используется для угадывания номера SSID. Неоднозначные соответствия не получают придуманного имени. UI хранит связь в модели памяти; редактируемого bridge-поля нет.

Пользовательский сертификат дополнительно проверяется на роутере до импорта и генерации TOML: каждый PEM-блок должен успешно разбираться `openssl x509`. Некорректный первый или последующий блок, посторонний текст и незакрытые блоки отклоняются. Без OpenSSL непустой custom certificate не принимается; пустое поле использует обычное хранилище доверия клиента. Эта проверка предотвращает молчаливый fallback upstream при ошибке разбора, но не заменяет проверку TLS при соединении.

## DNS только из конфигурации подключения

Schema3 маршрутизации не содержит DNS. Порт 53 TCP/UDP выбранных источников направляется на **внутренний транзитный адрес 192.0.2.53** в TUN. Это не адрес внешнего DNS-сервера и не значение dns_upstreams; его не нужно вводить пользователю. Core TrustTunnel перехватывает DNS и передаёт запрос обработчику с endpoint.dns_upstreams, включая настроенные DoH/DoT и нестандартные порты. Проверка перед запуском отвергает локальную коллизию транзитного адреса.

Для этого пути DNS конфигурации обязателен при запуске. В стабильном коде v1.1.5 при пустом dns_upstreams запрос может идти на исходный адрес назначения; поэтому аддон не запускает такое подключение и не добавляет запасного резолвера. Пустой список при импорте сохраняется. Значения DNS не публикуются в status.json, поскольку URL резолвера может содержать приватные параметры.
