# Ручное обновление TrustTunnel CLI

Функция alpha.7 обновляет только клиент в `/opt/trusttunnel/bin`, не код аддона или прошивку. На AX86U 30.09.2026 выполнено обновление кнопкой панели 1.1.5 → 1.1.7; фактические результаты и ограничения — в [TEST-REPORT.md](TEST-REPORT.md). Первичная установка остаётся закреплённой на проверенном 1.1.5; схема конфигурации не расширяется автоматически для новых версий.

## Работа из панели

1. В обзоре выберите канал. «Устанавливать ночные сборки» означает выбор nightly для следующего поиска и ручной установки; фонового обновления нет. Изменение канала сбрасывает предыдущий результат поиска.
2. Нажмите «Проверить обновления». Загружаются только метаданные официальных GitHub releases для Linux aarch64. Stable исключает prerelease; nightly требует явной метки nightly. Результат действует час и связан с записанным hash установленного клиента. Замена binary другим способом требует нового поиска; несовпадающие метаданные версии не показываются как текущая версия.
3. Проверьте установленную и доступную версии. «Обновить CLI» устанавливает именно показанную сборку после подтверждения. Переключение канала может предложить более старую версию: кнопка выбирает последнюю сборку канала, а не обещает повышение версии относительно другого канала.
4. Работающий VPN перезапускается. Существующая пауза сохраняется. Выбранные сети сохраняют защитные правила; остальные сети не включаются в VPN. После установки проверьте сайт и внешний IP с выбранной сети.

Начиная с alpha.8 панель показывает «Последняя установка CLI» и «Последняя проверка» с датой и временем браузера. Дата установки записывается после успешного запуска/фиксации метаданных, дата проверки — после успешного получения релизов. Смена канала, обновление и перезагрузка сохраняют последнюю проверку в приватном `client-last-check.json`; кандидат на установку всё равно требует нового поиска и действует час. Сбой поиска не стирает дату предыдущего успеха. Старые установки без сохранённого времени показывают «Дата неизвестна», а не вымышленную дату; для проверенной установки 1.1.7 на текущем AX86U время отдельно перенесено из подтверждённой операции alpha.7.

На 30.09.2026 опубликованы stable 1.1.7 и beta 1.3.0-beta.1, но официальной публичной ARM64 nightly нет. В этом случае панель сообщает «не опубликована», установка недоступна. Beta и snapshot Conan из закрытого Artifactory не считаются nightly. Если upstream опубликует подходящий официальный nightly release с ожидаемым ARM64 архивом, digest и подписью, тот же механизм сможет его выбрать. Фактический формат такого будущего релиза пока не проверен.

Нужны curl, GnuPG (`gpg`), tar, timeout, od и штатные зависимости аддона. Setup устанавливает недостающие утилиты через Entware; существующая установка может показывать отсутствие зависимостей. Поиск требует только curl. Кнопки не выполняют Entware-wide upgrade и не устанавливают зависимости скрыто.

## Проверки перед заменой

- Принимаются только фиксированные HTTPS API/download URL официального TrustTunnelClient, точное имя ARM64 архива и SHA-256 из GitHub metadata. Нельзя передать произвольный URL или выполнить скачанный shell script.
- Release metadata повторно загружаются по ID перед скачиванием; изменение выбранного asset отклоняется. Архив ограничен 32 MiB, отдельный binary — 64 MiB; загрузка и распаковка имеют таймауты.
- Из архива через stdout извлекаются только два известных обычных файла: binary и его `.sig` внутри каталога, совпадающего с именем выбранного versioned ARM64 asset. Symlink/hardlink/дубликаты целевых файлов и небезопасное имя каталога отклоняются; другие члены архива не распаковываются на диск.
- GnuPG использует отдельный временный keyring и закреплённый первичный fingerprint `28645AC9776EC4C00BCE2AFC0FE641E7235E2EC6`. Подпись, ELF64 little-endian aarch64 и соответствие `--version` выбранному тегу проверяются до остановки старого процесса.
- Поиск, загрузка и проверка подписи освобождают контроллер для firewall/WAN refresh. Перед заменой заново берутся lock, проверяются кандидат/канал/срок/отсутствие транзакции. Guards проверяются и восстанавливаются перед остановкой клиента.

## Восстановление

Перед заменой сохраняются `trusttunnel_client.previous`, его SHA-256 и предыдущие метаданные; журнал с hash старого/нового клиента записывается атомарно. Замена binary выполняется на его файловой системе. Старый клиент возвращается при ошибке запуска нового; защита сохраняется даже при неудачном повторном запуске. Наличие TUN после обновления не доказывает работоспособность VPN.

Незавершённый журнал обнаруживается при запуске/refresh. Refresh сначала восстанавливает guards и только затем восстанавливает binary. Если автоматическое восстановление не завершается, можно вызвать по SSH:

```sh
/jffs/addons/trusttunnel/trusttunnel.sh recover-client
/jffs/addons/trusttunnel/trusttunnel.sh refresh
```

Восстановление принимает только известный старый/новый hash и обычные файлы. Неизвестная модификация или symlink требуют ручного разбора; контроллер их не перезаписывает. Повторная установка и удаление блокируются до разрешения журнала. `recover-client` относится к прерванной операции: после успешного обновления он не переключает версию обратно. Для ручного возврата после успешной установки применяется существующий проверяемый импорт binary из резерва при явно отключённом аддоне; обычная маршрутизация в этом случае временно возвращается, поэтому такой откат нужно выполнять осознанно.

Журнал и backups не являются гарантией восстановления после физического отказа USB/flash. Прерванная загрузка может оставить staging-файл; неизвестные файлы в `/opt/trusttunnel/bin` uninstaller сохраняет, а не удаляет по шаблону. Настоящая подпись 1.1.7 проверена на AX86U GnuPG 1.4.23. Аппаратные сбои питания/USB, отказ запуска новой версии, восстановление binary и утечки во время обновления ещё не проверены.

## Проверка трафика в обзоре

IP TUN показывает локальный внутренний адрес, не внешний выходной IP. «Проверить трафик» проверяет все ожидаемые собственные firewall rules, входные jumps, source rules и маршрут tt0, затем 10 секунд наблюдает счётчики разрешённых пересылаемых пакетов в обе стороны. Во время проверки откройте сайт с выбранного устройства.

Результат истекает через пять минут, после смены конфигурации или запуска клиента. Отсутствие пакетов означает необходимость повторить проверку с активным трафиком. Положительный результат подтверждает только наблюдаемый обмен; он не доказывает отсутствие DNS/IPv6/accelerated-flow обхода.

Для проверки блокировки предлагается отдельный контролируемый сценарий: гостевое устройство без мобильного Интернета → сайт работает → «Пауза с блокировкой» → новые IPv4/IPv6/DNS соединения перестают проходить → «Запустить» → доступ восстановлен. Основная управляющая сеть должна оставаться вне политики. На AX86U 30.09.2026 выполнена ограниченная проверка: пользователь подтвердил отсутствие Интернета во время паузы и возврат сайтов/VPN IP после запуска. IPv6 в Merlin был отключён; отдельные DNS/IPv6 запросы и пакетный захват не выполнялись, поэтому полный leak test не считается пройденным.
